# Hara 内置代码执行引擎

Hara Bot 负责理解需求、安排任务和向用户汇报；OpenCode 与 Pi 是后台执行能力，不是要求用户另外维护的聊天对象。当前接入仅对个人空间开放，组织执行策略保持独立。

## 使用方式

1. 在主 Bot 对话里描述代码需求及目标目录，例如「检查这个仓库的错误，并提出修复」。不需要先新建 OpenCode/Pi 会话。
2. Bot 通过 `runtime: "coding"` 委派任务，Hara 根据全局偏好解析出确定的引擎。启动、文件修改和合并仍受各自授权边界约束。
3. 需要用户选择或批准时，卡片出现在原 Bot 对话里；取消、过期、断线或任务换代后，旧卡片不能继续授权。
4. 代码修改保留在独立 Git worktree。Bot 可以检查 Diff，只有明确批准后才合并回源目录，不自动覆盖用户的改动。

Desktop 的「设置 → 应用与更新 → 代码执行引擎」提供：

- **自动**：目前固定推荐 OpenCode，是工程交付默认，不是性能排行榜或自动模型切换。
- **OpenCode**：内置运行时，经 Hara 的模型连接和受控工具执行。
- **Pi（实验性）**：内嵌 SDK，使用同一套 Hara 模型连接与工具边界。
- **Codex / Claude Code**：使用它们各自已有的本机登录；不会共享账号、复制认证凭据或替它们安装登录工具。

偏好只影响新建代码任务。已绑定的 worker、引擎和原生 session ID 不因设置变更而替换；继续任务使用原来的会话。保存偏好不等于引擎已登录或就绪，不能静默换到另一个引擎。

CLI 的可信宿主启动变量 `HARA_CODING_EXECUTOR=auto|opencode|pi|codex|claude` 可覆盖偏好，启动时捕获；存在覆盖时 Desktop 只读显示。项目配置、模型工具输入不能修改该变量或全局偏好。

## Agent 分工与已有编程会话（0.186.0）

这是两条独立路径，不能把「委派一个新代码任务」和「给用户正在使用的原会话补充消息」混为一谈：

- 新代码任务沿用前述 `runtime: "coding"`，按偏好使用 OpenCode/Pi/Codex/Claude，保留独立 worktree 与人工合并边界。
- 已有会话在当前 Agent 聊天框旁的「连接编程会话」中选择。右侧抽屉只读取有界的本机会话元数据，不自动选择、启动、恢复或复制会话。连接记录只属于这个对话，发送仍逐次显示确认卡。

### 已实现的第一阶段

1. 授权的常驻 Agent 可以通过 `agent_contact` 直接委派给同一 Space 内的同事，不必先绕到主 Hara Agent。每个根回合最多三层、八次委派；拒绝祖先回派、同时向同一接收者重复派单、已取消或换代的来源回合。计数不能因失败或释放接收者而重置。这是委派次数限制，**不是跨所有常驻 Agent 的 token 总预算**。
2. 子执行段保留根会话、根回合、直接父会话/回合、发起 Agent、执行 Agent 和深度。它仅作审计，不是重新授权；历史恢复不能复活旧的执行权。父任务负责人仍留在父对话，子执行段的执行人不是静默替换父任务负责人。
3. `session.coding-link.get/set` 保存用户选中的不透明会话地址、工作区摘要与连接代次。换绑使用 `expectedRevision` 防止并发覆盖，遵守对话控制租约和个人空间边界；即使尚未发第一条聊天，明确选中的连接也会落盘。fork 和委派不会复制连接。
4. `connected_coding_session` 只可访问这一地址。近期读回经过限长和脱敏；私有 worker 不允许被另一对话作为原生终端接管。每次消息发送都需新确认，即使是全自动模式也不例外；结构化原生引擎自己的问题/批准继续通过既有卡片机制处理。每个模型工具调用使用固定命令 ID 和持久回执，重放不会再次投递。原生发送结果不确定时保留未核销的持久回执，阻止同目标的新命令；换工具调用编号、换绑或重启都不会绕过，须显式读取原会话并确认已非活跃状态才能解除阻挡。终端通道在异步读取后再次检查取消，取消只关闭本次等待，不向原终端发 Ctrl+C。
5. 对共享 App Server 中独立运行的 Codex，只向经过再次核对的原活跃回合追加消息。此路径不 resume、不 fork、不 start 新回合、不订阅原执行，也不 interrupt；成功回执为 `accepted`，不等于原任务已完成，原权限仍由原控制端处理。投递通过父对话的工具回执呈现，不冒充原终端的回合开始/结束事件，也不因此自动刷新其他会话或解除未知投递的阻挡。若回合已结束或无法确认身份，拒绝发送，不改投其他窗口。接口依据：[Codex App Server](https://learn.chatgpt.com/docs/app-server)。
6. 飞书入站保留平台给出的 parent/root/thread 与 user/app 来源。无效字段明确标为不可用于路由，不从正文、前台窗口或最近活跃时间猜测归属。指定 Agent 的有界跟进需另行确认，规则见下文；不会默认开启群监听。

Claude Code 的 SDK continuation 不等于给任意独立 CLI/tmux 实例实时注入消息。历史会话须在高级恢复入口明确接入；本阶段不宣称任意终端都能直接收消息。已由 Hara 管理的原生会话沿用其实际能力和授权机制。连接界面的读取/绑定有超时和过期结果隔离，取消读取不会被当作另一次选择，也不会自动重试发送。

### 跨同事的交互闭环

常驻同事的普通批准和 `ask_user` 选择卡现在回到本次任务最初发起的 Agent 对话，不必切到同事的临时执行段。卡片显示真正执行者的昵称，不把内部路由路径当作聊天对象；同事继续委派的原生代码 worker 也保留这条归属链，但不伪装成普通 Hara 会话。

- `agent.delegated-interaction.v1` 独立协商常驻同事的交互；原生 worker 仍使用 `external.*` 协议及自己的真实不透明地址。普通同事不会获得虚构的 provider session ID。
- 批准只针对当前的一次操作，不提供「始终允许」或父任务授权转赠。回答必须对应原执行会话、原回合及未过期的问题，并服从发起对话当前的控制租约。昵称、路径和父会话等展示字段不能改变权限或投递对象。
- 根回合启动时捕获交互能力，旧客户端不能通过后来连入的新客户端补授权；断线只短暂保留原有效期内的未决卡片。取消、过期、配置或角色/空间边界变更时停止旧交互，不采用模型给出的默认答案，也不把未回答的任务写成完成回执。
- 重连的权威快照只向明确请求的原始发起对话恢复卡片，不落到旧版批准列表、子会话快照或其他空间。待选答案仅保存在当前进程内；重启不会复活旧批准。

隔离的双层常驻同事 → 普通文件批准/问题，以及同事 → 原生 worker 批准/问题已纳入回归。这里的模拟提供方测试和真实 Desktop 组件测试不代表任意终端或飞书公网的全链路验收。

### 指定 Agent 跟进飞书线程

在同一台设备的个人空间中，可在 Agent 聊天里要求某位同事跟进明确的飞书回复线程。主 Hara 可以委派，同事也可以直接负责，不必让每条消息绕回主 Agent。前提是已有的飞书连接已经启动、发信人已获授权，且本人在群里的新消息明确 @ 了该机器人。

- `agent_followup list` 只列出最近一小时的有界候选元数据，不保存未授权的消息正文。模型只能提名候选 ID，不能自填账号、发信人、工作区、父对话或原生会话。原消息、回复链、负责 Agent、时长和次数会显示在新的确认卡里；选择不明确时先问用户。
- 确认后，仅接收同账号、同群、同一获授权人及同回复链的新文字消息。每次授权最多 24 小时、8 条，间隔至少 30 秒；同设备最多并行两次跟进。旧消息、app/bot、未知来源、多匹配或矛盾回复链不能获得执行权，也不落入私聊的全自动执行路径。
- 负责 Agent 只在已授权的工作区内处理。写文件、命令和给已连接编程会话发消息仍逐次确认，即使父对话是全自动模式也不能免除。不会从群消息开启新引擎、任意临时 subagent、插件或新监听；已有原生会话地址也不会随委派转赠。
- 批准和问题卡回到原始 Hara 聊天，显示实际负责同事。每次结束或需要人工继续时，只回复该次输入的飞书原消息线程，不向全群另发通知。原生发送的 `accepted` 回执不等于原代码任务已经完成。
- `agent_followup status/stop` 可在原聊天查询或撤销。本机私有账本在 `~/.hara/gateway/agent-followups.json`，记录来源、负责 Agent、执行段、任务/回合与投递回执；消息正文处理后清除，状态工具不返回正文或原始发信人 ID。最多保留 64 个授权、512 个事件，达到上限拒绝新增，不自动丢弃未核销回执。
- 本次确认的 Hara 客户端必须在线。断线、控制权切换、暂停/迁移、角色/设置变更、发信人撤权及到期会暂停。重启不恢复执行权、不重做排队或已开始的任务；旧账本不会被显示成仍在运行。重新跟进需显式撤销旧授权、选择新来源并重新确认。
- 投递前先持久化发送状态。发送结果不确定或执行崩溃时保留隔离回执，不自动重发、重跑或改投另一个窗口。任务暂停/失败不会被重复的“继续”触发成循环。

这是本人确认的有限线程跟进，不是全天候全群机器人或跨设备 Relay。合成测试覆盖入站归属、双层同事委派、原聊天交互、逐次批准、线程闭环和重启/撤销边界；尚未据此宣称真实飞书公网或任意独立 tmux/Claude CLI 注入已验收。

### 后续任务与验收条件

- **交互真实验收**：仍需真实提供方和打包 Desktop 的验收；不能把隔离的委派回执、模拟卡片测试等同于全部业务链路已经完成。
- **高级恢复入口**：默认工作流保留 Agent 聊天与对话旁的精确连接；旧页面收在设置的编程会话恢复/诊断入口。隐藏主导航入口不停止或删除现有会话。未知/冲突目标只澄清，不擅自开启终端。
- **真实验收与发布**：隔离模型、假 App Server、WebSocket、窄窗口测试与真实终端/飞书公网验收分开记录。没有用户授权时，不为验证而发送真实群消息或中断正在进行的工作。

## 安装与运行时

- npm 安装固定版本的 Pi SDK 和匹配平台的 OpenCode 原生 optional dependency。不要使用 `--omit=optional`，也不需要额外安装 OpenCode/Pi 应用。
- Desktop 使用独立校验的 OpenCode sidecar；Pi SDK 随 Hara 引擎编译。Desktop 构建使用 `desktop-sidecar` 模式，避免再在 CLI sidecar 内嵌一份相同运行时。开发源码通过检查不等于当前旧 sidecar 已升级，正式打包必须锁定包含这些修改的 CLI tag/commit。
- standalone 构建从 lockfile 指定的官方 npm tarball 校验 SHA-512，为每个目标嵌入对应 OpenCode 原生文件；macOS 在原生构建机为副本签名后再嵌入。运行时按内嵌 SHA-256 校验并释放到用户私有缓存，不联网下载、不执行 npm 安装脚本、不从 PATH 寻找替代命令。
- Bun 1.3.9 的 musl 构建需要显式传入匹配的 `bun-linux-arm64-musl` 或 `bun-linux-x64-musl-baseline` 目标；无法确认 libc 时拒绝猜测。跨平台构建成功仍须在目标系统执行 native runtime smoke，不能视为已经验收。
- 显式 Desktop sidecar 无效、安装包缺失或缓存内容不匹配时拒绝执行并显示修复提示，不让 Codex/Claude 的注册一起崩溃，也不偷偷调用系统里同名的程序。
- OpenCode 原生包较大。部分 musl 平台的 npm 安装可能同时保留两种 Linux optional 包；运行时只选择匹配的一个，不代表两个都执行。
- 许可声明随 npm 包和编译后的 CLI 交付，可离线运行 `hara licenses` 查看。

## 权限、状态与用量

OpenCode/Pi 只获得临时回环模型地址和单次随机凭据，不获得真正的服务商 Key。模型请求回到同一个 Hara Provider；真实模型、连接代次、profile、worker、turn 和 worktree 绑定在 Hara 内部校验。

工具只开放 `read_file`、`write_file`、`edit_file`、`list_files`、`ask_user`。上游自带 shell、插件、扩展、技能、认证刷新和更新机制不启用。**当前这两个受控 worker 没有任意 shell / 构建 / 测试执行工具**；不能把生成代码或模型自述当作已运行测试，主 Bot 必须单独使用具备相应授权的验证能力并保留证据。这是有意保留的权限边界，不是完整照搬上游 CLI。

会话使用不透明 ID，持久消息与私有 continuation 有完整性校验及连接代次隔离；邮箱只在对应输入确实被受理、消费并落盘后核销，失败不冒充投递成功。任务预算由 Hara 模型/工具 host 的实时计数决定，不采用可能缺失或重复的 SDK usage 估算。取消后的已发出输入也计入父任务，不重复累计；缺失实际 usage 时使用保守输入估算，不能据此换算订阅余额或费用。

Pi 同时待处理的补充消息按原顺序进入下一模型回合，不为每条排队消息另起一轮；各消息仍单独持久化，并在成功结束后按 ID 核销。取消或失败不提前核销。此行为不等于合并不同任务、放宽预算或允许消息授予工具权限。

编程专用工具说明与实际白名单保持一致，不再推荐该 worker 不具备的 grep、shell 或 apply_patch。工具参数约束和每次修改的授权检查不变；精简说明减少的是静态请求字节，不能直接换算成 token、延迟或账单降幅。
