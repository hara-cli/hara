# Jev × Hara：真实体验视频记录

这份记录用于拍摄第一支真实体验视频，也作为实现边界和验收清单。主线不是“给微信加一个
自动回复插件”，而是让 Hara 的所有高后果动作先经过同一个 Action Guard；微信只是第一条
可见、容易复现的入口。

## 一句话叙事

用户仍然只对 Hara 说自然语言。Hara 在真正点击、输入、发送或执行破坏性命令之前，把一份
经过脱敏、去标识、结构化的动作摘要交给 Jev。Jev 只返回 `allow / review / block` 及概率，
不生成回复、不执行工具，也不获得新的权限；最终决定仍由 Hara 的确定性规则、组织策略和
人工审批共同完成。

## 当前已经接入的边界

- 微信、飞书及桥接群的文字外发（`channel_message send`）
- 当前聊天的文件外发（`send_file`）
- 桌面应用的激活、点击、输入和按键；截图、查找、移动鼠标不调用 Jev
- 打开真实系统浏览器；URL 的账号、查询参数和片段不会进入决策状态
- 已有的高危命令和越界文件写入
- Docker 全局清理、容器强删、卷删除、`docker compose down -v`

这些动作共用同一入口。以后接浏览器的上传、提交、发布、支付，或者接日历、云盘和其他 IM，
只需在同一动作分类器中声明后果，不再各写一套“微信特例”。

## 三种模式

| 模式 | Jev 的作用 | Hara 的实际行为 |
| --- | --- | --- |
| `shadow` | 旁路观察并显示概率 | 完全保留原 Guardian 行为，适合录第一版视频和积累样本 |
| `advisory` | `review/block` 转为人工复核 | Jev 不直接硬拦截；没有真人审批通道时不执行 |
| `enforce` | `block` 可拦截，`review` 必须真人确认 | Jev 不可用时降级为复核，不会在无人值守任务里静默放行 |

任何模式下，Jev 的 `allow` 都不能绕过权限规则、组织策略、应用白名单或原有人工审批。

## 拍摄前配置

不要在录屏中输入或展示密钥。先在录屏外通过受保护的环境注入 `TYPESAFE_API_KEY`，然后只
录下面这些非敏感配置：

```bash
hara config set decisionEngine typesafe
hara config set decisionMode shadow
hara config set decisionModel jev-latest
```

可选自定义地址：

```bash
hara config set decisionBaseURL https://api.typesafe.ai
```

仅仅存在 `TYPESAFE_API_KEY` 不会自动启用 Jev；必须显式设置 `decisionEngine=typesafe`。这避免
用户无意间把任务摘要发送给外部判断服务。

## 第一支视频脚本（微信场景）

### 1. 先证明“不是每一步都调用 Jev”

1. 在 Hara 中查看一个文件或让它总结当前目录。
2. 屏幕上不应出现 Jev 收据。
3. 旁白：普通读取、截图、搜索和项目内编辑仍走确定性快路径，零额外网络判断。

### 2. 从微信发起一次明确的跨渠道发送

1. 在微信中对 Hara 说：`给已连接的测试群发：Jev 联调完成，请只回复收到。`
2. Hara 解析出已保存目标，准备调用统一的外发动作。
3. 拍到 Hara 的收据，例如：`Jev shadow · allow 91% · effective allow`。
4. 拍到目标群收到消息以及 Hara 的真实送达回执；“已排队”不能剪成“已送达”。
5. 旁白：动作目标只保留 `weixin / feishu / bridge` 类型，没有联系人、群 ID、账号或密钥。

### 3. 展示“不确定就复核”

1. 切换：`hara config set decisionMode advisory`。
2. 给一个边界不清的外发请求，例如正文明确、接收方表述含糊的测试消息。
3. Jev 返回 `review` 时，Hara 必须显示一次真人确认；不确认就不发送。
4. 不要为了画面故意给真实联系人发送误导或骚扰内容，使用专门测试群。

### 4. 展示故障降级

1. 使用测试环境模拟 Jev 不可用，再切换 `enforce`。
2. 发起外发或桌面输入动作。
3. 有真人通道时应转为复核；无人值守任务应明确拒绝，而不是假装成功。
4. 恢复服务后再执行一遍，证明失败没有遗留半次发送。

## 隐私检查（发布前逐项看）

- 不出现 TypeSafe、模型供应商、Hara Control 或 IM 的密钥、Cookie、授权头
- 不出现真实联系人、群 ID、组织 ID、手机号、邮箱、内部域名和私聊正文
- 只使用测试账号、测试群和专门准备的无敏感项目
- 浏览器地址栏不保留查询参数；终端不执行会回显密钥的命令
- 剪辑不能把 `queued`、`accepted` 或“系统已接收”说成“对方已收到”

## 还能用在哪些地方

Jev 适合替代“让大模型写一段文字再解析”的小判断，并可减少主模型调度轮次：

- 多 Agent 的角色选择、任务路由和候选排序
- 网关消息的分流：忽略、回复、建任务、转人工
- 自然语言审批答复的结构化判断
- 模型/供应商故障后的兼容候选排序（健康状态仍由确定性探针决定）
- 回复发送前的风险、引用和敏感信息检查

后续接入这些能力时要单独做评测。Jev 不用于写代码、生成回复、规划长任务、判断接口是否
真的健康，也不替代 Hara 的权限与审计系统。第一版先用 Action Guard 的真实数据验证准确率、
延迟和成本，再决定哪些路由可以正式从主模型迁移给 Jev。

## 本轮实现小结（视频口播备忘）

- Hara 先用纯代码做后果分类，普通读文件、截图、检索和项目内编辑不产生 Jev 请求。
- `shadow` 同时保留旧 Guardian，目的是真实对比，不宣称提速。
- `advisory / enforce` 成功取得 Jev 判断后会替代旧的自由文本 Guardian 调用，因此高风险动作
  少一次通用模型回合；收据显示真实延迟、实际模型版本、观察判断和最终生效判断。
- Jev 的低置信度 `allow` 和低置信度 `block` 都归入 `review`：不因为不确定而误放行，也不因为
  不确定而错误硬拦截。
- Hara 只发送有长度上限、经过密钥脱敏的最新用户指令和待执行动作，不发送完整历史；动作
  目标中的联系人、群 ID 和账号会被移除。最新指令和拟发送正文仍可能含有用户自己写入的业务
  信息，因此该能力保持显式启用，真实视频必须只用测试数据。Jev 不能执行工具，也不能扩大
  Hara 原有权限。
- 当前最适合拍的是微信跨渠道外发，但同一机制已经覆盖飞书、浏览器打开、桌面点击/输入、
  文件外发、高危 Shell 和 Docker 数据删除动作，不是微信专用插件。
